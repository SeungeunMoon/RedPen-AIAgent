# 금융광고 AI 사전심의 에이전트 — 2일 MVP 기획서

Oct 20, 2026 · @seungeun moon

## 한눈에

**2일 안에 "규정 RAG + 공시 대조 + 근거 달린 판정 리포트"가 끝까지 도는 것을 만들고, 골든셋으로 수치를 내는 것**이 목표입니다. 기능을 넓히기보다 한 경로를 끝까지 완성하는 데 집중합니다.

| 항목 | MVP 결정 | 이유 |
| --- | --- | --- |
| 사용자 | 은행 준법감시 부서의 광고 심의 담당자 1명 | 근거, 인용 검증, 규정 버전이 가치를 갖는 사람 |
| 업권·상품 | 은행 정기예금·적금 광고 | 공시 API로 금리를 객관적으로 대조할 수 있음 |
| 입력 | 광고 문안 텍스트 붙여넣기 + 공시 상품 선택 | PDF·이미지는 파싱 비용 대비 증명 가치가 낮음 |
| 산출 | 문구별 판정 리포트 (위반 유형, 근거 조문 원문, 시행일, 수정안) | 이 제품의 핵심 주장 그 자체 |
| 위반 유형 | 4개 (필수사항 누락, 공시 불일치, 단정·과장, 보장·오인) | 2일 안에 라벨링과 평가가 가능한 범위 |
| 평가 | 골든셋 40건, ablation 3개 구성 | "왜 RAG인가"를 숫자로 답하기 위해 |

## 문제와 사용자

심의 담당자는 올라온 광고안을 규정, 상품설명서, 공시 금리와 하나씩 대조해 의견서를 씁니다. 심의 물량은 늘고 규제는 강해지는데, 중소형사에는 이 일을 나눌 인력이 없습니다.

- **물량:** 디지털 마케팅 확대로 심의 대상이 꾸준히 증가하고 있습니다 ([딜사이트](https://dealsite.co.kr/articles/162808)).
- **반복 패턴:** 보험 광고 위반 4만 7,078건 중 61.4%가 미심의이고, 나머지 대부분이 필수 기재사항 누락입니다 ([조세금융신문](https://www.taxnet.co.kr/contents/news/news-detail?id=31714)). 사람이 매번 확인하기엔 단순하고, 놓치면 비쌉니다.
- **인력 공백:** 대형 협회는 AI 심의 시스템을 자체 구축 중이지만 ([SBS Biz](https://biz.sbs.co.kr/amp/article/20000314051)), 중소형 금융사는 내부통제 전담 인력부터 부족합니다 ([딜사이트](https://dealsite.co.kr/articles/164903)).

**사용자:** 중소형 은행·저축은행 준법감시 부서의 광고 심의 담당자

**JTBD:** 광고안이 올라왔을 때, 1차 대조가 끝난 상태에서 시작해서, 근거가 확실한 심의 의견을 빨리 확정하고 싶다.

광고를 만든 현업 직원은 이 MVP의 사용자가 아니라 "광고안을 보낸 사람"으로만 존재합니다.

## 솔루션

광고 1건을 4단계로 처리합니다. 상품 유형은 예·적금으로 고정했기 때문에 분류 단계는 없습니다.

1. **클레임 추출:** 금리(기본·최고), 기간, 우대 조건, 단정·보장 표현, 필수 기재사항 존재 여부를 JSON으로 뽑습니다.
2. **규정 검색:** 조문 단위 인덱스에서, 오늘 기준으로 유효한 버전만 검색합니다.
3. **대조와 판정:** 광고 금리를 공시 API 값과 비교하고, 검색된 조문을 근거로 문구별 위반 유형, 등급, 수정안을 냅니다.
4. **인용 검증:** 판정이 인용한 조문을 법제처 API에서 다시 받아와 문언을 대조합니다. 일치하지 않으면 한 번 재검색하고, 그래도 실패하면 "사람 확인 필요"로 강등합니다.

**법 개정 대응:** 인덱스에는 조문마다 시행일을 붙여 검색 시점의 유효 버전만 고릅니다. 최종 근거는 4단계에서 원천 API로 재확인하므로, 인덱스가 낡아도 낡은 근거가 리포트에 나가지 않습니다. 정기적인 변경 동기화는 MVP 이후로 미룹니다.

## MVP 범위와 요구사항

### 넣는 것과 빼는 것

| 넣는다 | 뺀다 (MVP 이후) |
| --- | --- |
| 예·적금 텍스트 광고 | 대출, 증권(ETF), 보험 광고 |
| 위반 유형 4개 | 심의필 표시, 투자성 수익률 유형 |
| 조문 시행일 필터 + 원천 API 재확인 | 정기 변경 동기화, 과거 광고 재검사 |
| 판정별 동의·기각 버튼 (시간 남으면) | 요청·승인·반려 결재 워크플로 |
| 리포트 화면 1개 | 로그인, 권한, 마케터 화면, PDF·이미지 입력 |

### P0 요구사항

| ID | 요구사항 | 완료 기준 |
| --- | --- | --- |
| R1 | 규정 적재 | 금소법, 시행령, 감독규정이 조문 단위로 적재되고, 청크마다 법령명, 조문 번호, 시행일이 있다 |
| R2 | 클레임 추출 | 광고 1건에서 스키마에 맞는 JSON이 나온다. 스키마 검증 실패 시 1회 재시도한다 |
| R3 | 공시 대조 | 선택한 상품의 공시 기본·최고 금리와 광고 금리가 다르면 두 값을 나란히 표시한다 |
| R4 | 판정 | 의심 문구마다 위반 유형(4개 중 하나), 등급, 근거 조문 1개 이상, 수정안을 낸다 |
| R5 | 인용 검증 | 인용 조문을 원천 API에서 재조회해 일치하지 않으면 강등한다. 존재하지 않는 조문이 리포트에 나가면 실패다 |
| R6 | 리포트 화면 | 문구 하이라이트, 근거 원문, 시행일, 수정안이 한 화면에 보인다 |
| R7 | 평가 스크립트 | 골든셋 전체를 한 번에 돌려 지표 표를 출력하고, 구성을 바꿔 ablation을 돌릴 수 있다 |

## 데이터

MVP에서 실제로 쓰는 데이터는 5종입니다. 이 중 골든셋만 직접 만들고, 나머지는 공개 API나 공개 문서입니다.

| 데이터 | 출처 | 받는 방법 | 쓰는 곳 |
| --- | --- | --- | --- |
| 금융소비자보호법, 시행령 | [법제처 Open API](https://open.law.go.kr/LSO/openApi/guideList.do) | API 키(OC) 발급 후 조항호목 조회 | R1 적재, R5 재조회 |
| 금융소비자 보호에 관한 감독규정 | 법제처 Open API (행정규칙) | 같은 키 | R1 적재 |
| 금융광고규제 가이드라인 | [금융위원회 보도자료](https://www.fsc.go.kr/no010101/76045) 첨부 | 수동 다운로드 | R1 적재 (해석 기준) |
| 정기예금·적금 금리 | 금감원 "금융상품 한눈에" 오픈API ([토요경제](https://www.sateconomy.co.kr/news/view/179589018945297)) | 이용 신청 후 JSON | R3 대조 |
| 골든셋 40건 | 직접 구축 | 아래 참고 | R7 평가 |

**골든셋 구성:**

- 정상 광고 10건: 은행 홈페이지 예·적금 이벤트 문안을 수집하고, 출처 URL과 수집일을 함께 저장합니다.
- 합성 위반 25건: 정상 문안에 위반 유형을 1개씩 주입합니다. 유형당 6건 이상이 되도록 맞춥니다.
- 경계 사례 5건: 광고가 아닌 공지, 애매한 표현처럼 "사람 확인 필요"가 정답인 사례입니다.

문구 단위로 라벨링합니다. 필드는 광고 ID, 문안, 상품 ID, 위반 문구 위치, 위반 유형, 정답 조문입니다. 공개 저장소에는 수집 원문 대신 합성 문안과 출처 링크만 올립니다.

## 평가

골든셋 40건으로 지표 4개를 재고, 같은 골든셋에서 구성 3개를 비교합니다. 40건은 통계적으로 작으므로, 결과는 "방향성 확인"으로 보고합니다.

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 위반 탐지 재현율 | 라벨된 위반 문구 중 탐지된 비율 | 80% 이상 |
| 근거 조문 정확도 | 인용 조문이 정답 조문과 일치하는 비율 | 85% 이상 |
| 환각 인용 | 존재하지 않는 조문 인용 수 | 0건 |
| 처리 시간 | 광고 1건 p95 | 60초 이내 |

**Ablation 구성:**

1. **LLM 단독:** 규정 없이 프롬프트만 사용
2. **전체 규정 주입:** 적재한 규정 전체를 컨텍스트에 통째로 넣음
3. **RAG + 인용 검증:** 최종 구성

2번과 3번의 비교가 "왜 RAG인가"에 대한 답입니다. 결과가 비슷하게 나오면 "규정이 작을 땐 통째로 넣어도 되고, 업권이 늘면 RAG가 필요하다"는 결론을 근거와 함께 씁니다.

## 2일 일정

반나절 단위 4블록입니다. 각 블록의 완료 기준을 못 넘기면 다음 블록에서 범위를 줄이고, 평가 블록(Day 2 오후)은 줄이지 않습니다.

| 블록 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 시작 전 (1시간) | 아키텍처 확정, [ADR](https://claude.ai/code/artifact/69a50afd-bce9-4263-b9da-28ecdaa12122) 001\~009 검토, API 키 발급 확인 | 결정마다 대안과 재검토 조건이 적혀 있음 |
| Day 1 오전 | 법제처 API로 규정 적재 (R1), MCP 서버 2개를 stdio로 연결, LangSmith 트레이스 연결, 위반 유형 4개의 정답 조문 확정 | 조문 검색 쿼리 1개가 시행일 필터와 함께 동작하고, 그 호출이 LangSmith에 보임 |
| Day 1 오후 | 골든셋 40건 제작, 추출·검색·판정 v0 (R2\~R4) | 골든셋 1건이 끝까지 돌아 판정 JSON이 나옴 |
| Day 2 오전 | 인용 검증 (R5), SSE 이벤트 스트림, 리포트 화면 (R6) | 화면에서 광고 입력 → 단계 진행 표시 → 리포트 확인이 됨 |
| Day 2 오후 | 평가 스크립트 (R7), ablation 3개 실행, README와 데모 영상 | 지표 표와 ablation 표 완성 |

**기술 스택 (확정):**

- **FastAPI 서버 1개:** API, AI 파이프라인(추출·검색·판정·검증), 평가 스크립트를 모두 여기에 둡니다 (ADR-008).
- **실시간 전송:** `POST /api/runs`로 검토를 만들고 `GET /api/runs/{run_id}/events`로 SSE를 구독합니다. 이벤트는 `stage`, `verdict`, `error`, `done` 4종류입니다 (ADR-005, 006).
- **MCP 서버 2개 (korean-law, fin-disclosure):** 각각 `.py` 파일로 만들고, FastAPI가 stdio 자식 프로세스로 띄웁니다. 앱 시작 시(`lifespan`) 한 번 띄워 세션을 유지하고, 종료 시 닫습니다. MCP 서버의 로그는 stderr로만 출력합니다 (ADR-002).
- **LLM:** 개발은 Ollama, 골든셋 평가와 데모는 OpenAI API. OpenAI SDK의 `base_url`과 모델명만 설정으로 바꿉니다. Ollama로 낸 지표는 보고하지 않습니다 (ADR-010).
- **임베딩:** OpenAI text-embedding-3-small을 개발과 평가 모두에 고정해서 씁니다 (ADR-011).
- **캐시:** 각 MCP 서버 프로세스 안의 TTL 딕셔너리로 처리합니다 (ADR-007).
- **데이터:** PostgreSQL + pgvector (Docker Compose).
- **관측성:** LangSmith 무료 플랜으로 트레이스를 수집하고, 상태 객체 JSON은 증적으로 따로 저장합니다 (ADR-009).
- **화면:** Vue 3 + Vite 단일 페이지 (ADR-012).

세부 개발 계획은 [개발 준비 계획](https://claude.ai/code/artifact/f4d2a4f5-6375-49a4-946a-19fb9acbca05)에 있습니다.

**Redis는 쓰지 않습니다.** 서버가 하나라 작업 큐가 필요 없고, 캐시는 프로세스 내부로 충분합니다. 서버 인스턴스가 여러 개가 되어 캐시를 공유하거나 외부 API 호출량을 전체적으로 제한해야 할 때 도입합니다.
