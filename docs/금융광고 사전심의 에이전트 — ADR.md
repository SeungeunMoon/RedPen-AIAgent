## ADR-001 에이전트 구조

**배경:** 광고 1건의 심의는 추출, 규정 검색, 판정, 근거 검증 순서로 진행됩니다. 금융권에서는 같은 광고에 대해 판정 경로를 매번 같게 설명할 수 있어야 합니다.

**결정:** 코드로 고정한 워크플로(상태 그래프) 안에 역할이 좁은 LLM 에이전트 4개(추출, 검색, 판정, 검증)를 배치합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 단일 프롬프트 (규정 + 광고를 한 번에) | 구현이 가장 빠름, 호출 1회 | 어느 단계에서 틀렸는지 측정할 수 없음, 인용 검증 불가 |
| **B. 고정 워크플로 + 좁은 에이전트** | 단계별 평가와 ablation 가능, 경로 재현 가능 | LLM 호출 수와 지연 증가 |
| C. 자율 에이전트 (모델이 경로 결정) | 예상 못한 입력에 유연 | 경로가 매번 달라 설명이 어렵고, 비용 폭주와 오류 누적 위험 |

**선택 이유:** 심의는 단계가 정해진 업무입니다. 단계를 고정하면 판정 경로를 재현할 수 있고, 단계별로 지표를 재서 어디를 고쳐야 할지 알 수 있습니다.

**결과와 트레이드오프:** 호출 수가 늘어 지연이 커지는데, 판정 워커를 병렬로 돌려 줄입니다. 고정 단계에 맞지 않는 새로운 유형의 광고에는 유연성이 떨어집니다.

**재검토 조건:** 업권이 늘어 광고마다 필요한 단계가 달라지면 앞단에 라우팅을 추가합니다. 고정 단계로 처리되지 않는 사례가 평가셋의 상당 부분을 차지하면 구조를 다시 봅니다.

## ADR-002 MCP 서버 실행 방식

**배경:** 법제처 API와 금감원 공시 API를 각각 MCP 서버로 감싸 에이전트가 호출합니다. MCP 서버를 실행하는 방법은 여러 가지입니다.

**결정:** FastAPI 백엔드가 MCP 서버 2개(`.py`)를 stdio 자식 프로세스로 실행합니다. 앱 시작 시(`lifespan`) 한 번 띄워 세션을 유지하고, 종료 시 닫습니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. In-process 라이브러리 통합 (직접 import) | 가장 단순, 프로세스 경계 없음 | MCP 프로토콜의 이점(다른 클라이언트에서 재사용, 경계 분리)이 없음, 장애 격리 없음 |
| **B. 자식 프로세스 + stdio** | MCP 프로토콜을 그대로 사용, 배포 단위는 하나, 네트워크 설정 불필요 | 앱과 수명을 같이함, 인스턴스가 늘면 프로세스도 중복, stdout 오염 주의 |
| C. 원격 HTTP MCP 서비스 (별도 컨테이너) | 독립 배포와 확장, 여러 클라이언트가 공유 | 컨테이너, 인증, 네트워크 구성이 필요해 2일 안에 과함 |

**선택 이유:** 1인 2일 조건에서 Docker 컨테이너를 늘리지 않고도 "외부 데이터는 MCP 경계를 지난다"는 설계를 실제 프로토콜로 보여줄 수 있습니다.

**결과와 트레이드오프:** MCP 서버 프로세스가 죽으면 재기동 로직이 필요합니다. MCP 서버의 로그는 stderr로만 출력해야 합니다. stdout은 JSON-RPC 메시지 통로이기 때문입니다.

**재검토 조건:** 앱 인스턴스가 2개 이상이 될 때, 다른 팀이나 MCP 클라이언트가 같은 서버를 공유해야 할 때, 내부망과 외부 호출 구간을 네트워크로 분리해야 할 때 C로 전환합니다.

## ADR-003 RAG 수행 방식

**배경:** 규정 검색을 파이프라인이 항상 수행할지, LLM이 필요할 때 고를지, 별도 서비스로 뺄지 정해야 합니다. 광고 문구("무조건 받는")와 법 조문("단정적 판단을 제공")은 어휘가 달라서 한 번의 고정 질의로는 놓치는 경우가 생깁니다.

**결정:** 검색 **단계 자체는 파이프라인에 고정**하고, 그 단계 안에서 검색 에이전트가 `search_articles`를 tool로 최대 3회 호출하며 질의를 고칩니다. A와 B를 섞은 형태입니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 고정 RAG 파이프라인 (같은 질의로 1회 검색) | 재현성이 가장 높음, 가장 단순 | 어휘 차이 때문에 재현율이 낮음 |
| B. Agent Tool로 호출 (LLM이 검색 여부와 질의 결정) | 유연, 질의 재작성 가능 | 모델이 검색을 건너뛰면 근거 없는 판정이 나옴 |
| C. 별도 RAG 마이크로서비스 | 독립 확장, 여러 서비스가 공유 | 2일 안에 과함, 네트워크 홉 추가 |
| **A + B 혼합** | 검색을 건너뛸 수 없음(근거 강제) + 질의 재작성의 재현율 | 검색 호출이 최대 3배, 일부 비결정성 |

**선택 이유:** "근거 없는 판정은 내보내지 않는다"가 제품의 핵심 원칙이라 검색은 반드시 일어나야 합니다. 동시에 어휘 차이를 메우려면 질의 재작성이 필요합니다.

**결과와 트레이드오프:** 검색 호출 수와 비용이 늘어나고, 같은 입력에도 질의가 조금씩 달라질 수 있습니다. 실행마다 질의 목록을 증적에 남겨 추적합니다.

**재검토 조건:** 평가에서 질의 재작성이 재현율을 의미 있게 올리지 못하면 A로 단순화합니다. 규정 코퍼스를 여러 서비스가 함께 쓰게 되면 C로 분리합니다.

## ADR-004 MCP 기능 범위

**배경:** MCP 서버는 tools(모델이 골라 호출하는 함수), resources(읽기 전용 데이터), prompts(재사용 템플릿)를 노출할 수 있습니다. 어디까지 쓸지 정해야 합니다.

**결정:** MVP는 **tools만** 씁니다 (korean-law의 `get_article`, fin-disclosure의 `get_product_rates`). 상용 설계에서는 고정 데이터(체크리스트, 위반 분류표)는 resources로, 심의 의견서 템플릿은 prompts로 노출합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **A. 모든 기능을 tools로만** | 구현이 단순하고 클라이언트 호환성이 가장 높음 | 고정 데이터도 모델이 호출해야 해서 호출이 낭비됨 |
| B. tools + resources + prompts 모두 사용 | 고정 데이터는 컨텍스트에 바로 들어가고, 템플릿을 재사용할 수 있음 | 구현량이 늘고, 클라이언트마다 지원 수준이 다름 |
| C. MCP 없이 내부 API로 분리해 통신 | 익숙한 방식, 프로토콜 학습 불필요 | 다른 MCP 클라이언트에서 재사용할 수 없음 |

**선택 이유:** MVP에서 MCP로 감싸는 대상은 외부 API 2개뿐이고, 둘 다 "모델이 언제 부를지 고르는" 조회입니다. 체크리스트와 분류표는 로컬 규정 모듈에서 바로 읽으므로 resources가 필요 없습니다.

**결과와 트레이드오프:** MVP 코드만 보면 MCP의 일부만 쓴 것으로 보입니다. 상용 설계(아키텍처 문서의 MCP 서버 설계)에서 B를 쓰는 이유를 함께 설명해야 합니다.

**재검토 조건:** compliance-kb를 MCP 서버로 올릴 때, 또는 심의 담당자가 MCP 클라이언트로 서버를 직접 쓰기 시작할 때 B로 확장합니다.

## ADR-005 실시간 전송 방식

**배경:** 광고 1건 검토에 최대 60초가 걸립니다. 그동안 화면이 멈춰 있으면 사용자는 실패했다고 판단합니다. 추출, 검색, 판정, 검증 중 어디까지 진행됐는지 보여줘야 합니다.

**결정:** SSE(Server-Sent Events)로 단계별 진행 이벤트를 스트리밍합니다. FastAPI `StreamingResponse`로 구현합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| 동기 응답 | 가장 단순 | 최대 60초 무응답, 프록시 타임아웃 위험 |
| **SSE** | 서버에서 클라이언트로 단방향, 일반 HTTP 그대로, 브라우저가 자동 재연결 | 클라이언트에서 서버로는 보낼 수 없음 |
| WebSocket | 양방향 | 연결 관리와 프록시 설정이 필요한데, 이 화면에는 양방향이 필요 없음 |
| Long Polling | 호환성이 가장 넓음 | 요청이 반복되고 구현이 지저분함 |

**선택 이유:** 필요한 건 "서버가 진행 상황을 흘려보내는 것" 하나뿐입니다. 단방향이면 SSE가 가장 적은 비용으로 충분합니다.

**결과와 트레이드오프:** 사용자가 검토 도중 중단하거나 조건을 바꾸려면 별도 HTTP 요청이 필요합니다.

**재검토 조건:** 검토 도중 사용자와 에이전트가 주고받는 상호작용(중단, 질의 수정, 대화형 조문 질의)이 생기면 WebSocket을 검토합니다.

## ADR-006 프론트 이벤트 프로토콜

**배경:** SSE로 무엇을 어떤 형식으로 보낼지 정해야 합니다. 이 화면은 대화가 아니라 단계 진행 상황과 문구별 판정이 쌓이는 구조화된 리포트입니다.

**결정:** 자체 SSE 이벤트 스키마를 정의합니다.

```json
{"event": "stage",   "data": {"stage": "retrieve", "status": "started"}}
{"event": "verdict", "data": {"claim_id": "c1", "code": "V2", "severity": "violation", "article_id": "…", "verified": true}}
{"event": "error",   "data": {"stage": "factcheck", "message": "공시 API 응답 없음"}}
{"event": "done",    "data": {"run_id": "run_…"}}
```

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. Vercel AI SDK 프로토콜에 백엔드를 맞춤 | 검증된 프론트 라이브러리로 스트리밍 UI를 빠르게 만듦 | 채팅 메시지 스트림 중심이라 단계 진행과 구조화된 판정을 억지로 끼워 맞춰야 함 (80%는 되고 20%가 안 되는 경우) |
| **B. 자체 이벤트 스키마** | 화면 구조와 정확히 일치, 이벤트 4종류로 단순 | 클라이언트 파싱과 상태 관리를 직접 구현 |

**선택 이유:** 표준 라이브러리를 쓰는 게 대개 낫지만, 이 화면에는 그 라이브러리가 가정하는 "메시지"가 없습니다. 이벤트가 4종류뿐이라 직접 구현 비용도 작습니다.

**결과와 트레이드오프:** 프론트에서 이벤트를 받아 상태를 직접 갱신해야 합니다. 브라우저 `EventSource`는 GET만 지원하므로, `POST /runs`로 검토를 생성해 `run_id`를 받고 `GET /runs/{run_id}/events`로 스트림을 구독하는 2단계로 나눕니다. 스키마를 바꾸면 프론트와 백엔드를 함께 고쳐야 하므로 이벤트 스키마는 코드 한 곳에 정의합니다.

**재검토 조건:** 조문 Q&A 같은 채팅형 기능을 추가하면 그 화면에 한해 A를 씁니다.

## ADR-007 저장소와 인메모리 DB

**배경:** 규정 청크와 임베딩, 실행 증적, 심의 피드백을 저장해야 합니다. 벡터 DB를 따로 둘지, 인메모리 DB(Redis)를 쓸지도 정해야 합니다.

**결정:** PostgreSQL + pgvector 하나에 모두 저장합니다(Docker Compose). Redis는 쓰지 않습니다. 외부 API 응답 캐시는 각 MCP 서버 프로세스 안의 TTL 딕셔너리로 처리합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **A. PostgreSQL + pgvector** | 판정과 근거 청크를 외래 키로 연결, 트랜잭션 보장, 저장소 1개 | 청크가 매우 많아지면 전용 벡터 DB보다 검색 성능이 떨어짐 |
| B. 전용 벡터 DB + RDB | 벡터 검색 성능과 기능이 좋음 | 저장소가 2개가 되고, 판정과 근거의 연결을 앱에서 맞춰야 함 |
| C. SQLite 또는 로컬 파일 벡터 DB | 설치가 필요 없음 | 동시성이 약하고, 상용 설계와 구조가 달라짐 |
| (추가) Redis 사용 | 작업 큐, 공유 캐시 | 서버가 하나라 큐가 필요 없고, 캐시는 프로세스 내부로 충분 |

**선택 이유:** 이 제품의 핵심은 "이 판정이 어떤 버전의 어떤 조문을 근거로 했는가"를 증명하는 것입니다. 증적과 인덱스가 같은 DB에 있으면 외래 키로 이 연결을 보장할 수 있습니다. 예·적금 규정은 수천 청크 이내라 pgvector로 충분합니다.

**결과와 트레이드오프:** 프로세스 내부 캐시는 서버를 재시작하면 비워집니다. 프로토타입에서는 문제가 되지 않습니다.

**재검토 조건:** 앱 인스턴스가 2개 이상이 되어 캐시를 공유하거나 외부 API 호출량을 전체적으로 제한해야 하면 Redis를 도입합니다. 업권 확장으로 청크가 수십만 개 단위가 되면 전용 벡터 DB를 검토합니다.

## ADR-008 백엔드 구성

**배경:** 상용 설계는 Spring Boot API와 Python AI 서비스를 분리합니다. 2일 프로토타입에서도 그렇게 할지 정해야 합니다.

**결정:** FastAPI 서버 1개에 API, AI 파이프라인, 평가 스크립트를 모두 둡니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. Spring Boot API + FastAPI AI 서비스 분리 | 역할 분리, 금융권에서 익숙한 구조, Java 역량을 보여줄 수 있음 | 서비스 2개, 서비스 간 통신과 배포가 2배 |
| **B. FastAPI 단일 서버** | Python AI 생태계(MCP SDK, 평가 도구)를 그대로 사용, 프로세스 1개 | 인증, 권한, 트랜잭션 관리 같은 엔터프라이즈 기능이 약함 |
| C. Spring Boot 단일 서버 | Java 스택 하나로 통일 | RAG 실험과 평가 반복 속도가 Python보다 느림 |

**선택 이유:** 2일 동안 증명할 대상은 AI 파이프라인과 평가 결과입니다. 서비스를 나누는 데 쓰는 시간이 그 증명을 줄입니다.

**결과와 트레이드오프:** 인증과 권한 관리는 MVP에서 빠집니다. 상용 구조와 다르다는 점을 아키텍처 문서에서 명시합니다.

**재검토 조건:** 로그인, 권한, 결재 워크플로를 붙이는 시점에 A로 분리합니다. 그때 FastAPI는 AI 서비스로 남고, 외부 API는 Spring이 맡습니다.

## ADR-009 관측성 도구

**배경:** 판정이 틀렸을 때 추출, 검색, 판정, 검증 중 어디서 틀렸는지 찾아야 고칠 수 있습니다. 상태 객체를 JSON으로 저장하는 것만으로는 단계별 입력, 출력, 도구 호출, 지연을 비교하기 어렵습니다.

**결정:** MVP는 LangSmith 무료 플랜(클라우드)으로 실행 트레이스를 수집합니다. 상태 객체 JSON 저장은 증적 용도로 그대로 유지합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **A. LangSmith 무료 (클라우드)** | 설정이 가장 빠르고 LLM 트레이스에 특화 | 트레이스 데이터가 외부 서버로 나감. 프라이빗 구성은 유료 |
| B. Langfuse 셀프호스팅 | 오픈소스, 내부망에 둘 수 있음 | Docker 컨테이너가 늘어남 |
| C. OpenTelemetry + LGTM 스택 | 업계 표준, 앱 메트릭·로그·트레이스를 한 곳에서 | 2일 안에 구성하기엔 무거움 |

**선택 이유:** 프로토타입에서 다루는 데이터는 공개된 광고 문안과 법령이라 외부로 나가도 문제가 없습니다. 디버깅을 Day 1부터 쓰려면 설정이 가장 빠른 쪽이 맞습니다.

**결과와 트레이드오프:** 트레이스가 외부 서버에 쌓이므로, 실제 금융사 데이터를 넣는 순간 이 선택은 성립하지 않습니다.

**재검토 조건:** 실제 금융사 광고안이나 사내 규정을 다루거나 내부망에 배포하면 B 또는 C로 전환합니다. 금융권 망분리 환경을 전제하면 B가 1순위입니다.

## ADR-010 LLM 공급자

**배경:** 개발 중에는 프롬프트와 배선을 수없이 고치며 LLM을 호출합니다. 이걸 전부 유료 API로 하면 비용이 들고, 로컬 모델만 쓰면 한국어 법률 판정 품질을 보장하기 어렵습니다.

**결정:** 개발은 Ollama 로컬 모델로 하고, 골든셋 평가와 ablation, 데모는 OpenAI API로 합니다. 두 공급자 모두 OpenAI SDK로 호출하고, `LLM_PROVIDER`와 `LLM_BASE_URL`, 역할별 모델명만 설정으로 바꿉니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 처음부터 OpenAI만 사용 | 개발과 평가의 모델이 같아 결과가 일관됨 | 반복 개발 중 비용이 계속 발생 |
| B. Ollama만 사용 | 비용 없음, 외부 전송 없음 | 판정 품질이 낮아 지표가 의미 없을 수 있음 |
| **C. 개발은 Ollama, 평가는 OpenAI** | 개발 비용을 줄이면서 지표는 성능 좋은 모델로 냄 | 공급자 간 구조화 출력 동작 차이를 게이트웨이에서 흡수해야 함 |

**선택 이유:** 개발 단계에서 필요한 건 "배선이 맞는가"이고, 평가 단계에서 필요한 건 "판정이 맞는가"입니다. 두 목적에 맞는 모델이 다릅니다.

**결과와 트레이드오프:** 게이트웨이에서 응답을 공급자와 관계없이 Pydantic으로 다시 검증하고 1회 재시도하는 경로가 필요합니다. Ollama로 낸 지표는 보고하지 않고, 모든 결과에 공급자와 모델명을 기록합니다.

**재검토 조건:** 금융사 망분리 환경을 전제하면 외부 API를 쓸 수 없으므로, 사설 모델이나 로컬 모델을 평가용으로도 써야 합니다. 그때는 B 또는 사설 모델로 다시 평가합니다.

## ADR-011 임베딩 모델

**배경:** 규정 인덱스와 검색 질의를 같은 모델로 임베딩해야 합니다. LLM처럼 개발과 평가에서 모델을 바꾸면 벡터 공간이 달라져 검색이 깨집니다.

**결정:** OpenAI text-embedding-3-small(1536차원)을 개발과 평가 모든 환경에서 고정으로 씁니다. 사용한 모델명을 청크 테이블에 함께 기록합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **A. text-embedding-3-small** | 1536차원이라 pgvector 일반 벡터 인덱스를 그대로 씀, 비용이 낮음 | large보다 표현력이 약할 수 있음 |
| B. text-embedding-3-large | 표현력이 더 좋음 | 3072차원이라 인덱스에 `halfvec` 타입이나 차원 축소가 필요 |
| C. Ollama 로컬 임베딩 모델 | 비용 없음, 외부 전송 없음 | 한국어 법률 문장 품질이 검증되지 않음, LLM과 함께 바뀌면 인덱스 재생성 필요 |

**선택 이유:** 청크가 수천 개 수준이라 모델 간 차이보다 청킹과 하이브리드 검색의 영향이 큽니다. 인덱스 구성이 가장 단순한 쪽을 고릅니다.

**결과와 트레이드오프:** 개발 중에도 OpenAI API 키가 필요합니다. 임베딩 코드는 LLM 게이트웨이와 분리해 공급자 설정이 같이 바뀌지 않게 합니다.

**재검토 조건:** 평가에서 검색 재현율이 목표에 못 미치고 원인이 임베딩으로 확인되면 B를 검토합니다. 망분리 환경이면 C 계열로 바꾸고 인덱스를 다시 만듭니다.

## ADR-012 프론트엔드

**배경:** 화면은 광고 입력, 상품 선택, 단계 진행 표시, 판정 리포트 하나입니다.

**결정:** Vue 3 + Vite 단일 페이지로 만듭니다. 라우터와 상태 관리 라이브러리는 쓰지 않고, SSE 구독은 composable 하나(`useRunEvents`)로 처리합니다. 개발 중에는 Vite 프록시로 `/api`를 FastAPI에 넘기고, 데모에서는 빌드 결과물을 FastAPI가 서빙합니다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 순수 HTML + JavaScript | 빌드 과정이 없음 | 상태 갱신과 컴포넌트 분리를 직접 해야 해서 화면이 커지면 지저분해짐 |
| **B. Vue 3 + Vite** | 익숙한 스택, 반응형 상태로 SSE 이벤트 반영이 간단 | 빌드 단계와 Node.js가 필요 |
| C. React + Vercel AI SDK | 스트리밍 UI 라이브러리가 많음 | 채팅 중심 프로토콜이라 이 화면과 맞지 않음 (ADR-006) |

**선택 이유:** 개발자가 이미 쓰는 스택이고, 이벤트가 올 때마다 화면을 갱신하는 데 반응형 상태가 잘 맞습니다.

**결과와 트레이드오프:** 개발과 데모의 서빙 방식이 다르므로, SSE가 Vite 프록시에서 버퍼링되지 않는지 첫날 확인합니다.

**재검토 조건:** 로그인, 이력 조회, 결재처럼 화면이 여러 개가 되면 라우터와 상태 관리 라이브러리를 도입합니다.
