# 금융광고 사전심의 에이전트 — 개발 준비 계획

Oct 20, 2026 · @seungeun moon

## 확정 사항과 주의할 점

개발은 **계약(스키마와 인터페이스)을 먼저 정하고, 끝까지 도는 뼈대를 만든 뒤, 부품을 하나씩 진짜로 바꾸는** 순서로 합니다. 결정 근거는 [ADR](https://claude.ai/code/artifact/69a50afd-bce9-4263-b9da-28ecdaa12122)에 있습니다.

| 영역 | 확정 | ADR |
| --- | --- | --- |
| 백엔드 | FastAPI 서버 1개 (API + AI 파이프라인) | 008 |
| MCP | korean-law, fin-disclosure를 stdio 자식 프로세스로 실행 | 002, 004 |
| 저장소 | PostgreSQL + pgvector, Redis 없음 | 007 |
| 실시간 전송 | SSE, 자체 이벤트 4종류 | 005, 006 |
| 관측성 | LangSmith 무료 | 009 |
| 임베딩 | OpenAI text-embedding-3-small (1536차원) | 011 |
| LLM | 개발은 Ollama, 평가와 데모는 OpenAI API. 게이트웨이에서 설정으로 교체 | 010 |
| 화면 | Vue 3 + Vite 단일 페이지 | 012 |

### 주의할 점 1. 임베딩은 개발 중에도 OpenAI로 고정

LLM은 Ollama로 바꿔도 되지만 **임베딩은 바꾸면 안 됩니다.** 인덱스를 만든 모델과 질의를 임베딩하는 모델이 다르면 벡터 공간이 달라서 검색이 깨집니다. 그래서 개발 환경에서도 임베딩만은 OpenAI API를 씁니다. 규정 청크가 수천 개 수준이라 비용은 거의 들지 않습니다.

**small을 고르는 이유:** large(3072차원)는 pgvector의 일반 `vector` 타입 인덱스가 지원하는 차원 한도를 넘어서, `halfvec` 타입을 쓰거나 차원을 줄여야 합니다. small(1536차원)은 그대로 HNSW 인덱스를 만들 수 있고, 수천 청크 규모에서는 성능 차이가 크지 않습니다.

### 주의할 점 2. Ollama 결과로 지표를 내면 안 됨

Ollama는 OpenAI 호환 API를 제공하므로, OpenAI SDK의 `base_url`만 바꾸면 같은 코드로 두 공급자를 오갈 수 있습니다. 다만 두 가지를 챙겨야 합니다.

- **구조화 출력 호환성:** JSON 스키마 강제 출력이 두 공급자에서 똑같이 동작한다고 가정하지 않습니다. 게이트웨이에서 응답을 Pydantic으로 검증하고, 실패하면 1회 재시도하는 공통 경로를 둡니다. 판정 워커의 "조문 ID enum 제한"도 이 검증에서 한 번 더 확인합니다.
- **성능 차이:** 로컬 모델은 한국어 법률 판정 품질이 크게 낮을 수 있습니다. **Ollama는 배선과 디버깅용이고, 골든셋 평가와 ablation, 데모는 OpenAI로 돌립니다.** 리포트에는 어떤 공급자와 모델로 낸 결과인지 항상 기록합니다.

### 주의할 점 3. Vue는 개발과 데모의 서빙 방식이 다름

- **개발:** Vite 개발 서버(5173)에서 `/api` 요청을 FastAPI(8000)로 프록시합니다. CORS 설정이 필요 없고, SSE도 프록시를 그대로 통과합니다.
- **데모:** `vite build` 결과물을 FastAPI가 정적 파일로 서빙합니다. 같은 출처라 CORS가 필요 없습니다.
- 라우터나 상태 관리 라이브러리는 쓰지 않습니다. 화면이 하나뿐이고, SSE 이벤트를 받는 composable 하나로 충분합니다.

## 1단계. 계정과 키 준비

| 필요한 것 | 용도 | 고려할 점 |
| --- | --- | --- |
| 법제처 Open API OC 키 | 규정 적재, 원천 재조회 | 승인 대기가 있을 수 있으니 가장 먼저 신청 |
| 금감원 "금융상품 한눈에" API 키 | 예·적금 금리 대조 | 키를 받으면 실제 응답을 한 번 받아 필드 구조부터 확인 |
| OpenAI API 키 | 임베딩 (개발·평가 공통), 평가·데모용 LLM | 사용량 한도를 걸어 비용 상한을 둠 |
| Ollama 설치와 로컬 모델 | 개발용 LLM | 한국어 출력과 JSON 출력이 되는 모델로, 로컬 메모리에 맞는 크기 선택 |
| LangSmith API 키 | 트레이스 | 환경변수만 설정하면 됨 |
| Docker | PostgreSQL + pgvector | pgvector가 포함된 공식 이미지 사용 |
| Node.js | Vue 3 + Vite | — |

**꼭 할 일:** 두 공공 API를 각각 한 번씩 호출해서 응답 원본을 `samples/` 폴더에 저장합니다. 이후 파서, MCP 서버, 테스트를 모두 이 샘플로 개발하면 API 장애나 호출 제한에 막히지 않습니다.

`.env.example`에 들어갈 키 목록:

실제 `.env`는 커밋하지 않습니다.

## 2단계. 데이터 준비

### 2-1. 규정 코퍼스

**대상:** 금융소비자보호법, 시행령, 감독규정(행정규칙), 금융광고규제 가이드라인(PDF)

청크 설계가 가장 중요합니다. 조문 단위로 자르되, 판정에서 인용할 단위(조·항·호)와 ID 규칙을 지금 정합니다.

```json
{
  "chunk_id": "금소법:22:3:1@2021-03-25",
  "law_id": "…",
  "law_name": "금융소비자 보호에 관한 법률",
  "article": 22, "paragraph": 3, "item": 1,
  "text": "…해당 호 원문…",
  "context": "제22조(…) ③ …",
  "effective_from": "2021-03-25",
  "effective_to": null,
  "embedding": "vector(1536)"
}
```

- **`context` 필드:** 호 하나만 잘라내면 무슨 조문인지 알 수 없습니다. 상위 조·항의 제목과 첫 문장을 함께 넣어 임베딩합니다.
- **ID 규칙은 한 번 정하면 바꾸지 않습니다.** 골든셋의 정답 조문, 판정의 `article_id`, 검증 단계의 재조회가 모두 이 ID에 묶입니다.
- **한국어 BM25:** PostgreSQL 기본 전문 검색은 한국어 형태소 분석을 지원하지 않습니다. 키워드 검색은 Python에서 메모리로 돌리고, 벡터 검색만 pgvector로 하는 하이브리드가 2일 안에 가장 빠릅니다. 청크가 수천 개 이하라 충분합니다.
- **가이드라인 PDF:** 법령과 형식이 달라서 Q&A 단위로 수동 분할하는 게 파서를 짜는 것보다 빠릅니다.
- **임베딩 일괄 처리:** 적재 스크립트에서 청크를 묶어 한 번에 임베딩하고, 모델명을 테이블에 함께 기록합니다. 나중에 모델을 바꾸면 전체를 다시 임베딩해야 한다는 표시입니다.

### 2-2. 공시 데이터 스냅샷

공시 금리는 매달 바뀝니다. 골든셋을 만든 뒤 API 값이 바뀌면 같은 평가를 다시 돌렸을 때 결과가 달라집니다. 골든셋에 쓰는 상품의 공시 응답을 **스냅샷으로 고정 저장**하고, 평가할 때는 MCP 서버가 스냅샷을 읽는 모드(`DISCLOSURE_MODE=snapshot`)로 동작하게 합니다.

### 2-3. 골든셋 40건

| 순서 | 할 일 | 고려할 점 |
| --- | --- | --- |
| 1 | 위반 유형 4개 ↔ 정답 조문 매핑표 확정 | 규정 적재가 끝나야 조문 ID로 적을 수 있음 |
| 2 | 정상 문안 10건 수집 | 출처 URL, 수집일, 연결할 공시 상품 코드를 함께 저장 |
| 3 | 합성 위반 25건 생성 | 정상 문안 하나에 위반 하나씩 주입. 어떤 규칙으로 변형했는지 기록 |
| 4 | 경계 사례 5건 | 정답이 "사람 확인 필요"인 사례 |
| 5 | **dev 15건 / test 25건으로 분리** | 프롬프트는 dev로만 튜닝하고 test는 마지막에 OpenAI로 한 번만 돌림 |

5번을 빠뜨리면 골든셋에 프롬프트를 맞춘 숫자가 나와서 지표의 의미가 없어집니다.

```
├─ samples/                     # 공공 API 응답 원본
├─ app/
│  ├─ main.py                   # FastAPI, lifespan에서 MCP 서버 기동, 빌드된 web 정적 서빙

│  ├─ schemas/                  # Pydantic: Claim, Verdict, ReviewRun, SSE 이벤트

│  │  ├─ graph.py               # 단계 순서, 병렬, 재시도

│  └─ fin_disclosure/server.py
├─ ingest/                      # 법령 수집, 파싱, 청킹, 임베딩, 공시 스냅샷
├─ eval/
│  ├─ goldenset/{dev,test}.jsonl
│  ├─ run_eval.py, metrics.py
│  └─ configs/                  # ablation 3개 + 공급자 설정
├─ web/                         # Vue 3 + Vite
│  ├─ vite.config.ts            # 개발 시 /api → localhost:8000 프록시
│  └─ src/
│     ├─ App.vue
│     ├─ components/            # AdInput, ProductPicker, StageProgress, VerdictList
│     ├─ composables/useRunEvents.ts   # EventSource 구독, 상태 갱신
│     └─ types.ts               # SSE 이벤트와 리포트 타입
└─ tests/
```

**고려할 점:**

- **`app/schemas/`가 단일 진실 원천입니다.** API 응답, SSE 이벤트, 상태 객체, 평가 스크립트가 모두 같은 Pydantic 모델을 씁니다. 프론트의 `web/src/types.ts`는 이 스키마에서 OpenAPI로 생성하거나, 최소한 이벤트 4종류를 손으로 맞춰 둡니다.
- **프롬프트는 파일로 둡니다.** 상태 객체의 `versions.prompt`에 파일 해시를 기록하면 어떤 프롬프트로 이 결과가 나왔는지 재현됩니다.
- **LLM과 임베딩을 다른 파일로 나눕니다.** LLM은 공급자를 바꿀 수 있지만 임베딩은 바꾸면 인덱스를 다시 만들어야 하므로, 설정과 코드를 분리해 실수로 같이 바뀌지 않게 합니다.
- **ingest와 eval은 앱과 분리된 스크립트입니다.** 앱이 떠 있지 않아도 실행됩니다.

## 4단계. 통신 정의

경계는 6개입니다. 전체 배치는 [아키텍처 문서의 2일 MVP 구조도](https://claude.ai/code/artifact/879d8d41-7602-45d0-8007-29b8082948d1)를 참고합니다. 가장 중요한 건 4-1과 4-2입니다.

### 4-1. Vue ↔ FastAPI (REST + SSE)

| 메서드 | 경로 | 요청 | 응답 |
| --- | --- | --- | --- |
| GET | `/api/products?bank=&q=` | 은행명, 상품명 | 후보 상품 목록 |
| POST | `/api/runs` | `{ad_text, product, as_of_date?}` | `202 {run_id}` |
| GET | `/api/runs/{run_id}/events` | — | `text/event-stream` |
| GET | `/api/runs/{run_id}` | — | 최종 리포트 JSON |
| POST | `/api/runs/{run_id}/verdicts/{claim_id}/feedback` | `{decision, reason}` | `204` (시간 남으면) |

- **실행과 구독의 분리:** `POST`는 백그라운드 실행만 시작하고 바로 반환합니다. 실행 중 이벤트는 run별 `asyncio.Queue`에 넣고 DB에도 저장합니다. 브라우저 `EventSource`가 GET만 지원하기 때문에 이렇게 나눕니다 (ADR-006).
- **재연결:** 이벤트마다 `id`를 붙이면 브라우저가 다시 붙을 때 `Last-Event-ID`를 보냅니다. 저장된 이벤트를 그 뒤부터 다시 보냅니다.
- **하트비트:** 판정 단계에서 10초 넘게 이벤트가 없을 수 있으니 15초마다 주석 줄을 보내 프록시가 연결을 끊지 않게 합니다.
- **Vite 프록시:** SSE 응답이 버퍼링되지 않는지 개발 첫날 확인합니다.

### 4-2. FastAPI ↔ MCP 서버 (stdio, JSON-RPC)

| 서버 | 도구 | 입력 | 출력 |
| --- | --- | --- | --- |
| korean-law | `law_get_article` | `law_id`, `article`, `paragraph?`, `item?`, `as_of_date` | `chunk_id`, `text`, `effective_from`, `fetched_at` |
| fin-disclosure | `disclosure_get_product_rates` | `fin_co_no`, `product_code` | 기간별 기본·최고 금리, 공시 기준월, `fetched_at` |

- **에러는 결과로 돌려줍니다.** "조문 없음", "원천 API 시간 초과"는 예외가 아니라 에러 표시와 코드(`NOT_FOUND`, `UPSTREAM_TIMEOUT`)를 담은 도구 결과로 반환합니다. 오케스트레이터가 강등으로 처리할 수 있어야 합니다.
- **클라이언트 타임아웃:** 도구 호출마다 10초 제한을 둡니다.
- **동시 호출:** 판정 워커가 병렬로 돌면 같은 세션에 호출이 동시에 들어갑니다. 첫날 동시 호출 테스트를 하고, 문제가 있으면 서버당 동시 호출 수를 `asyncio.Semaphore`로 제한합니다.
- **재기동:** 자식 프로세스가 죽으면 다시 띄우는 로직을 `mcp_client/manager.py`에 둡니다.
- **stdout 금지:** MCP 서버에서 `print`를 쓰지 않고 로그는 stderr로만 보냅니다 (ADR-002).

### 4-3. FastAPI ↔ PostgreSQL

테이블 5개: `regulation_chunk`, `review_run`, `verdict`, `reviewer_feedback`, `run_event`(SSE 재연결용). 비동기 드라이버로 연결합니다.

### 4-4. FastAPI ↔ LLM (게이트웨이)

- **공급자 교체:** Ollama와 OpenAI 모두 OpenAI SDK로 호출하고, `LLM_PROVIDER`, `LLM_BASE_URL`, 역할별 모델명만 설정으로 바꿉니다.
- **구조화 출력 + 검증:** 각 에이전트의 출력 스키마를 Pydantic에서 JSON 스키마로 만들어 넘기고, 응답은 공급자와 관계없이 Pydantic으로 다시 검증합니다. 실패하면 1회 재시도합니다.
- **판정 워커의 동적 스키마:** `article_id`를 검색 결과 ID 목록의 enum으로 호출할 때마다 만듭니다.
- **재현성:** temperature 0, 모델명 고정, 호출마다 공급자, 모델, 토큰 수, 지연을 기록합니다.

### 4-5. FastAPI → OpenAI 임베딩

적재할 때와 검색 질의를 만들 때 같은 모델을 씁니다. 질의 임베딩은 실행 중 호출이므로 타임아웃과 재시도를 둡니다.

### 4-6. FastAPI → LangSmith

환경변수로 연결하고, 트레이스 메타데이터에 `run_id`, 프롬프트 버전, 공급자, ablation 구성 이름을 넣습니다.

## 5단계. 내부 계약

단계마다 입력과 출력, 시간 예산을 정합니다. 전체 60초를 나눠 두면 어디서 느려지는지 바로 보이고, 타임아웃 기준도 생깁니다. 시간 예산은 OpenAI 기준이며, Ollama는 로컬 성능에 따라 더 걸릴 수 있습니다.

| 단계 | 입력 | 출력 | 시간 예산 |
| --- | --- | --- | --- |
| extract | 광고 문안 | `Claim[]` (인용 구절, 위치, 유형) | 8초 |
| retrieve | `Claim` 1개 | 후보 청크 ID 목록, 사용한 질의 | 10초 (최대 3회 호출) |
| factcheck | 금리 `Claim`, 상품 | 불일치 목록 | 5초 |
| judge | `Claim` + 후보 청크 + 대조 결과 | `Verdict` (유형, 등급, 조문 ID, 수정안) | 15초 (병렬) |
| verify | `Verdict` | 검증 결과 (실재, 문언 일치, 근거 적합성) | 15초 |

검증 단계의 "근거 적합성"은 조문이 실재하고 문언도 맞지만 그 판정을 실제로 뒷받침하지 않는 경우(misgrounded)를 잡는 검사입니다 ([참조 조사](https://claude.ai/code/artifact/899f2697-be9a-4746-b012-46bad1e5f8e3)).

## 6단계. 개발 순서

1. **걸어가는 뼈대:** 모든 노드를 가짜 응답을 내는 스텁으로 만들고, Vue 화면 → POST → SSE → 리포트까지 끝까지 한 번 돌게 합니다. 이 시점에 통신 경계가 전부 연결됩니다.
2. **MCP 서버 2개를 진짜로 교체:** `samples/` 응답으로 먼저 개발하고, 그다음 실제 API로 전환합니다.
3. **규정 적재와 검색을 진짜로 교체:** OpenAI 임베딩으로 인덱스를 만듭니다.
4. **골든셋 제작과 평가 스크립트:** 노드를 하나 교체할 때마다 dev셋으로 돌려 지표를 확인합니다.
5. **추출 → 판정 → 검증 순서로 진짜로 교체:** Ollama로 배선과 디버깅을 합니다.
6. **OpenAI로 전환해 평가:** `LLM_PROVIDER=openai`로 바꿔 ablation 3개를 dev셋에서 돌리고, 마지막에 test셋을 한 번만 돌립니다.
7. **화면 마무리와 데모:** `vite build` 결과물을 FastAPI에서 서빙하고, 데모 영상과 README를 만듭니다.

각 단계가 끝날 때마다 화면에서 광고 하나를 넣어 끝까지 도는지 확인합니다. 마지막 날 연결에서 터지는 일을 막는 가장 확실한 방법입니다.
