# 금융광고 사전심의 에이전트 — 아키텍처 제안

Oct 20, 2026 · @seungeun moon

## 결론

**자율 에이전트가 아니라, 코드로 고정한 워크플로 안에 역할이 좁은 LLM 에이전트 4개를 배치하는 구조**를 제안합니다. 역할은 추출, 검색, 판정, 검증입니다. 외부 데이터는 MCP 서버 3개로 분리합니다.

- **왜 워크플로인가:** 심의는 단계가 정해진 일이고, 금융권에서는 "왜 이 판정이 나왔는지" 매번 같은 경로로 설명할 수 있어야 합니다. 경로를 모델이 정하는 자율 에이전트는 이 요구와 맞지 않습니다.
- **왜 그래도 멀티 에이전트인가:** 추출, 판정, 검증은 실패 방식이 서로 다릅니다. 하나의 프롬프트에 몰면 어디서 틀렸는지 측정할 수 없고, 나눠야 단계별로 평가하고 고칠 수 있습니다.
- **왜 MCP인가:** 법령, 공시, 사내 규정은 출처와 신뢰도, 배포 위치가 다릅니다. 서버 단위로 나누면 내부망 배포 시 서버만 교체하면 되고, 모든 외부 조회가 한 경계를 지나므로 감사 로그를 남기기 쉽습니다.

각 결정의 대안 비교와 재검토 조건은 [ADR 문서](https://claude.ai/code/artifact/69a50afd-bce9-4263-b9da-28ecdaa12122)에 001\~009로 정리했습니다.

## 참조 패턴

뼈대는 Anthropic의 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)에 정리된 패턴입니다. 이 글은 예측 가능성이 중요한 정형 작업에는 미리 정한 코드 경로로 LLM과 도구를 엮는 **워크플로**를, 단계 수를 미리 알 수 없는 열린 문제에는 **에이전트**를 권합니다. 이 기획에서 쓰는 패턴은 4개이고, 쓰지 않는 패턴도 이유와 함께 적었습니다.

| 패턴 | 정의 | 이 기획에서 쓰는 곳 | 맞는 이유 |
| --- | --- | --- | --- |
| Prompt chaining | 단계별로 LLM을 이어 호출하고 중간에 코드 검사(gate)를 둠 | 추출 → 검색 → 판정 → 검증의 전체 뼈대 | 심의 단계가 고정되어 있고, 단계마다 스키마 검증 gate를 둘 수 있음 |
| Parallelization (sectioning) | 독립된 하위 작업을 병렬로 나눠 실행 | 의심 문구별, 위반 유형별 판정 워커 | 한 호출이 한 관점만 보면 정확도가 오르고, 병렬이라 지연이 줄어듦 |
| Evaluator-optimizer | 한 LLM이 만들고 다른 LLM이 평가해 피드백하는 루프 | 인용 검증 에이전트 → 검색·판정 재시도 | 평가 기준이 명확함 (조문이 실재하고 문언이 일치하는가) |
| Augmented LLM | 검색, 도구, 메모리로 확장된 LLM | 검색 에이전트가 질의를 스스로 고쳐 조문을 찾음 | 광고 문구와 법 조문의 어휘 차이를 질의 재작성으로 메움 |
| Routing | 입력을 분류해 전용 처리로 보냄 | MVP에서는 안 씀. 업권(은행·증권·보험) 확장 시 도입 | 예·적금만 다루는 동안은 분류할 대상이 없음 |
| 자율 에이전트 | 모델이 스스로 경로와 도구를 결정하는 루프 | 쓰지 않음 | 비용과 오류 누적이 커지고, 판정 경로를 매번 같게 설명하기 어려움 |

같은 글이 강조하는 원칙도 그대로 따릅니다. 복잡도는 성능이 실제로 오를 때만 더하고, 도구 정의(agent-computer interface)에 프롬프트만큼 공을 들입니다. 그래서 아래 Tools 명세는 실수하기 어렵게(poka-yoke) 인자를 설계했습니다.

## 에이전트 구성

오케스트레이터는 LLM이 아니라 **코드로 짠 상태 그래프**입니다. LLM은 4개의 좁은 역할에만 쓰고, 계산이나 대조처럼 정답이 정해진 일은 결정적 함수로 처리합니다.

| 구성 요소 | 종류 | 하는 일 | 쓰는 도구 | 실패 시 |
| --- | --- | --- | --- | --- |
| 오케스트레이터 | 코드 (상태 그래프) | 단계 순서, 병렬 분기, 재시도 횟수, 사람 확인 지점 관리 | — | 최대 반복 도달 시 "사람 확인 필요"로 종료 |
| 추출 에이전트 | LLM, 구조화 출력 | 광고 문안에서 금리, 기간, 조건, 표현, 필수 기재사항을 JSON으로 추출 | `locate_span` | 스키마 검증 실패 시 1회 재시도 |
| 검색 에이전트 | LLM + 도구 루프 (최대 3회 호출) | 의심 문구별로 질의를 만들고 조문을 찾음, 결과가 약하면 질의를 고침 | `search_articles`, `get_checklist` | 근거를 못 찾으면 "근거 없음" 표시 |
| 판정 워커 (병렬) | LLM, 구조화 출력 | 문구 1개 × 위반 유형 1개 단위로 판정, 근거 조문 ID와 수정안 생성 | 검색 결과만 근거로 사용 | 검색 결과에 없는 조문 ID는 스키마에서 거부 |
| 공시 대조 | 결정적 함수 | 광고 금리·기간과 공시 값을 비교 | `get_product_rates`, `compare_rates` | API 장애 시 "대조 미수행" |
| 검증 에이전트 | LLM + 도구 | 인용 조문을 원천에서 재조회해 문언 일치와 논리 적합성 평가, 피드백 생성 | `get_article` | 불일치 시 피드백과 함께 검색·판정으로 1회 되돌림, 재실패 시 강등 |
| 사람 확인 | 심의 담당자 | 판정별 동의·기각과 사유 입력 | — | 기각 사유는 평가 데이터로 저장 |

&#91;embedded content: 에이전트 흐름 · LLM 4역할, 코드 3단계, 검증 루프 1개\]

추출 뒤에 검색·판정과 공시 대조가 나뉠고, 두 결과가 판정 워커에서 합쳐진 뒤 검증을 거쳐 사람에게 갑니다.

**판정 워커의 핵심 장치:** 판정 워커의 출력 스키마에서 `article_id`는 검색 단계가 넘겨준 ID 목록 중에서만 고를 수 있게 enum으로 제한합니다. 모델이 조문 번호를 지어낼 길을 구조적으로 막는 것입니다. 검증 에이전트는 그 위에서 "조문은 실재하지만 이 위반에 맞지 않는" 경우를 잡습니다.

## Tools 명세

LLM에 노출하는 도구는 모두 **읽기 전용**입니다. 증적 저장처럼 쓰기가 일어나는 동작은 오케스트레이터만 호출하고 모델에는 보여주지 않습니다.

| 도구 | 위치 | 입력 | 출력 | 사용 주체 | 실수 방지 설계 |
| --- | --- | --- | --- | --- | --- |
| `search_articles` | compliance-kb MCP | `query`, `as_of_date`(필수), `law_ids`, `top_k` | 조문 ID, 법령명, 조문 번호, 원문, 시행 시작·종료일, 점수 | 검색 에이전트 | `as_of_date`를 필수로 둬서 버전 필터를 빼먹을 수 없게 함 |
| `get_article` | korean-law MCP | `law_id`, `article_no`, `as_of_date` | 원천 API에서 받은 현행 원문, 조회 시각 | 검증 에이전트 | 조문 번호를 "제22조 제3항" 같은 자유 문자열 대신 구조화 필드로 받음 |
| `get_checklist` | compliance-kb MCP (resource) | `product_type` | 필수 기재사항 목록과 각 항목의 근거 조문 ID | 검색 에이전트 | 상품 유형을 enum으로 제한 |
| `search_products` | fin-disclosure MCP | `bank_name`, `product_name` | 후보 상품 목록 (금융사 코드, 상품 코드) | 오케스트레이터 (입력 단계) | 상품 확정은 사람이 화면에서 선택 |
| `get_product_rates` | fin-disclosure MCP | `fin_co_code`, `product_code` | 기간별 기본·최고 금리, 우대 조건, 공시 기준월 | 공시 대조 | 공시 기준월을 항상 함께 반환 |
| `compare_rates` | 로컬 함수 | 추출된 금리 클레임, 공시 값 | 불일치 목록 (광고 값, 공시 값, 차이) | 공시 대조 | LLM 없이 숫자 비교만 함 |
| `locate_span` | 로컬 함수 | 광고 원문, 인용 구절 | 문자 위치 (시작, 끝) | 추출 에이전트 | 모델이 위치 숫자를 직접 세지 않게 함 |
| `save_evidence` | 로컬 (오케스트레이터 전용) | 실행 상태 전체 | 증적 ID | 오케스트레이터 | LLM에 노출하지 않음 |

`locate_span`을 별도 도구로 둔 이유는 위 글의 도구 설계 조언과 같습니다. 모델에게 문자 위치를 세게 하는 형식은 틀리기 쉬우므로, 모델은 구절만 인용하고 위치 계산은 코드가 합니다.

## MCP 서버 설계

MCP 서버는 **데이터의 출처와 신뢰 경계를 기준으로 3개**로 나눕니다. MCP는 서버가 tools(모델이 고르는 함수), resources(읽기 전용 데이터), prompts(재사용 템플릿)를 노출하는 프로토콜입니다 ([MCP SDK](https://github.com/modelcontextprotocol/typescript-sdk/pull/1171/files)). 그래서 모델이 고를 필요가 없는 고정 데이터는 tool이 아니라 resource로 둡니다.

| 서버 | 감싸는 원천 | Tools | Resources | Prompts | 배포 위치 (상용) |
| --- | --- | --- | --- | --- | --- |
| korean-law | [법제처 Open API](https://open.law.go.kr/LSO/openApi/guideList.do) | `get_article`, `search_law`, `get_amendment_history` | `law://{law_id}/{article_no}@{date}` | — | 외부 API 호출 구간 (DMZ) |
| fin-disclosure | 금감원 "금융상품 한눈에" 오픈API | `search_products`, `get_product_rates` | `product://{fin_co}/{product}` | — | 외부 API 호출 구간 |
| compliance-kb | 사내 규정 인덱스, 체크리스트, 위반 분류표 | `search_articles` | 체크리스트, 위반 유형 분류표, 업권 심의 기준 | 심의 의견서 템플릿 | 내부망 |

**이렇게 나눈 이유:**

- **신뢰 경계:** 외부 공개 데이터(법령, 공시)와 사내 데이터(심의 기준, 과거 판정)는 보안 등급이 다릅니다. 서버를 나누면 내부망 배포 시 compliance-kb만 안쪽에 두고 나머지만 외부 호출을 허용하면 됩니다.
- **재사용:** 같은 korean-law 서버를 심의 담당자가 Claude 같은 MCP 클라이언트에서 직접 "이 조문 현행 원문 보여줘"로 쓸 수 있습니다. 에이전트 전용 API가 아니라 사내 공용 도구가 됩니다.
- **감사:** 모든 외부 조회가 MCP 서버를 지나므로, 서버에서 요청·응답·시각을 기록하면 "이 판정은 이 시각에 받은 이 원문을 근거로 했다"가 증명됩니다.
- **교체 가능성:** 법제처 API가 막히면 korean-law 서버 내부만 로컬 원문 조회로 바꾸면 되고, 에이전트 코드는 그대로입니다.

**캐시:** `get_article`과 `get_product_rates` 결과는 각 MCP 서버 프로세스 안에서 (법령 ID, 조문 번호, 기준일) 같은 키로 캐시합니다. 별도 캐시 서버는 두지 않습니다. 다만 검증 단계는 "원천 재확인"이 목적이므로 캐시 TTL을 짧게(예: 24시간) 두고, 응답에 원천 조회 시각을 항상 포함합니다. 인스턴스가 늘어 캐시를 공유해야 하면 ADR-007의 재검토 조건에 따라 다시 결정합니다.

## 시스템 아키텍처

4개 계층으로 나눕니다. 핵심은 **모델 호출을 LLM 게이트웨이 한 곳으로 모으는 것**입니다. 금융권 배포 환경은 외부 API, 사설 클라우드 모델, 내부 sLLM 중 무엇이 허용될지 회사마다 다릅니다. 게이트웨이 뒤에서 모델만 바꿀 수 있어야 합니다.

| 계층 | 구성 요소 | 역할 | 권장 기술 |
| --- | --- | --- | --- |
| 표현 | 심의 화면 | 광고 입력, 리포트, 판정별 동의·기각 | Vue 단일 페이지 |
| 애플리케이션 | API 서버 | 인증, 요청 접수, 리포트 조회, 피드백 저장 | Spring Boot 또는 FastAPI |
| 애플리케이션 | 오케스트레이터 | 상태 그래프 실행, 병렬 분기, 재시도, 사람 확인 지점 | LangGraph 같은 상태 그래프 런타임, 또는 직접 구현 |
| 애플리케이션 | LLM 게이트웨이 | 역할별 모델 라우팅, 타임아웃, 토큰·비용 기록 | 단일 클라이언트 모듈 |
| 통합 | MCP 서버 3개 | 법령, 공시, 사내 규정 조회. 외부 API 응답은 서버 내부에서 캐시 | MCP Python 또는 TypeScript SDK |
| 데이터 | 규정 인덱스·증적 DB | 조문 청크, 임베딩, 시행일, 실행 증적 | PostgreSQL + pgvector |
| 데이터 | 적재 배치 | 법령 변경 이력 확인 후 바뀐 조문만 재적재 | 스케줄러 (상용), 수동 실행 (MVP) |
| 운영 | 관측성 | 실행별 트레이스, 도구 호출, 지연, 비용 | LLM 트레이싱 도구 (ADR-009) |

&#91;embedded content: 시스템 아키텍처 · 3개 네트워크 구간, MCP 서버 3개\]

사내 규정과 증적은 내부망에 남고, 법령·공시 조회는 외부 호출 구간의 MCP 서버만 나갑니다. 모델 호출은 LLM 게이트웨이 한 곳으로만 나갑니다.

벡터 DB를 별도 제품으로 두지 않고 PostgreSQL + pgvector를 쓰는 이유는 증적과 규정 인덱스가 같은 트랜잭션 경계 안에 있어야 하기 때문입니다. "이 판정이 어떤 버전의 어떤 청크를 근거로 했는가"를 외래 키로 묶을 수 있습니다.

## 상태와 증적 데이터 모델

오케스트레이터는 실행 1건의 상태 객체 하나를 단계마다 채워 나갑니다. 실행이 끝나면 이 객체가 그대로 증적이 됩니다. 같은 입력, 같은 규정 버전, 같은 프롬프트 버전으로 다시 돌렸을 때 결과를 비교할 수 있게 하는 것이 목적입니다.

```json
{
  "run_id": "run_20261020_0042",
  "input": {"ad_text": "…", "product": {"fin_co_code": "…", "product_code": "…"}},
  "as_of_date": "2026-10-20",
  "versions": {"prompt": "v3", "models": {"extract": "small", "judge": "large", "verify": "large"}, "index_snapshot": "2026-10-18"},
  "claims": [{"claim_id": "c1", "quote": "최고 연 4.5%", "span": [12, 21], "type": "rate"}],
  "retrieval": [{"claim_id": "c1", "article_ids": ["…"], "queries": ["…"]}],
  "fact_checks": [{"claim_id": "c1", "ad_value": 4.5, "disclosed_value": 3.8, "disclosure_month": "2026-10"}],
  "verdicts": [{"claim_id": "c1", "code": "V2", "severity": "violation", "article_id": "…", "fix": "…", "verification": {"status": "passed", "fetched_at": "…"}, "attempts": 1}],
  "reviewer_feedback": [{"claim_id": "c1", "decision": "accept", "reason": null}],
  "trace_id": "…"
}
```

| 테이블 | 핵심 필드 | 왜 필요한가 |
| --- | --- | --- |
| `regulation_chunk` | 조문 ID, 법령 ID, 조문 번호, 원문, 임베딩, 시행 시작일, 시행 종료일 | 시점별 유효 버전 검색 |
| `review_run` | 실행 ID, 입력, 기준일, 버전 묶음, 상태 | 재현성 |
| `verdict` | 실행 ID, 문구, 위반 코드, 등급, 조문 ID (외래 키), 검증 결과 | 판정과 근거의 연결 |
| `reviewer_feedback` | 판정 ID, 동의·기각, 사유, 시각 | 오탐 수집과 평가셋 확장 |

## 상용 수준 고려사항

금융권 배포에서 가장 먼저 부딪히는 건 모델 성능이 아니라 **망분리와 책임 소재**입니다. 아래 설계는 이 두 가지를 먼저 풀도록 짜여 있습니다.

| 영역 | 상황 | 설계 대응 |
| --- | --- | --- |
| 망분리 | 금융위는 2024년 망분리 개선 로드맵에서 샌드박스를 통한 생성형 AI 활용을 허용했고 ([금융위원회](https://fsc.go.kr/no010101/82885?curPage=92)), 2026년에는 SaaS 이용 관련 후속 개정이 나왔습니다 ([세종](https://shinkim.com/kor/media/newsletter/pdf/3105)). 다만 직원의 생성형 AI 사용을 전면 허용하는 단계는 아닙니다 ([딜사이트](https://dealsite.co.kr/articles/164691)) | LLM 게이트웨이 뒤에서 외부 API ↔ 사설 모델을 바꿀 수 있게 함. 광고 문안은 개인신용정보가 아니라는 점도 도입 논리에 씀 |
| 책임 소재 | AI가 최종 심의를 하면 판정 오류의 책임이 불분명함 | 사람 확인 단계를 그래프의 필수 노드로 둠. AI 출력은 "1차 의견"으로만 표기 |
| 설명 가능성 | 감독 대응 시 판정 근거를 재현해야 함 | 상태 객체 전체를 증적으로 저장, 버전 묶음 기록 |
| 안전장치 | 에이전트 루프의 비용 폭주와 오류 누적 | 검색 루프 최대 3회, 검증 재시도 1회, 단계별 타임아웃, LLM에는 읽기 전용 도구만 노출 |
| 관측성 | 어디서 틀렸는지 찾아야 개선 가능 | 실행별 트레이스로 단계별 입력·출력·도구 호출을 남김 |
| 평가 | 프롬프트나 모델을 바꿀 때 회귀 위험 | 골든셋 평가를 CI 게이트로 두고, 재현율·근거 정확도가 떨어지면 배포 차단 |
| 비용·지연 | 문구 수 × 유형 수만큼 판정 호출이 늘어남 | 추출은 소형 모델, 판정·검증은 대형 모델로 라우팅. 판정 워커는 병렬 실행, 조문 응답은 캐시 |

## 2일 MVP에서 구현할 범위

상용 구조의 **뼈대(상태 그래프, 역할 분리, MCP 경계, 증적)는 그대로 두고**, 운영 장치만 뺍니다. 면접에서 "상용이면 여기를 이렇게 확장한다"고 이 문서를 가리킬 수 있게 하는 것이 목적입니다.

| 구성 요소 | 상용 설계 | 2일 MVP | ADR |
| --- | --- | --- | --- |
| API·백엔드 | Spring Boot API + AI 서비스 분리 | **FastAPI 서버 1개**에 API와 AI 로직을 함께 둠 | 008 |
| 실시간 전송 | SSE | **SSE** (`POST /api/runs` 후 `GET /api/runs/{id}/events` 구독) | 005, 006 |
| 오케스트레이터 | 상태 그래프, 병렬 분기, 사람 확인 노드 | 상태 그래프 그대로. 병렬은 단순 동시 실행 | 001 |
| 에이전트 4개 | 역할별 모델 라우팅 | 역할 분리는 유지, 모델은 하나로 시작 | 001 |
| LLM | 외부 API 또는 사설 모델 | **개발은 Ollama, 평가·데모는 OpenAI** (게이트웨이 설정으로 교체) | 010 |
| 임베딩 | 망분리 시 사설 모델 | **OpenAI text-embedding-3-small**, 환경과 무관하게 고정 | 011 |
| 규정 검색 | 검색 에이전트가 tool로 최대 3회 호출 | 같음 | 003 |
| korean-law MCP | 3개 tool + resource, 캐시, 감사 로그 | `law_get_article` 1개 tool. **`.py` 서버를 stdio 자식 프로세스로 실행** | 002, 004 |
| fin-disclosure MCP | 2개 tool + resource | `disclosure_get_product_rates` 1개 tool. **stdio 자식 프로세스로 실행** | 002, 004 |
| compliance-kb MCP | 내부망 서버 | 로컬 모듈로 대체 (같은 함수 시그니처 유지) | 004 |
| 데이터 | PostgreSQL + pgvector | 같은 구성을 Docker Compose로 | 007 |
| 캐시 | MCP 서버 프로세스 내부 캐시 | 같음 (TTL 딕셔너리) | 007 |
| 관측성 | 셀프호스팅 트레이싱, 메트릭 | **LangSmith 무료** + 상태 객체 JSON 저장 | 009 |
| CI 평가 | 배포 게이트 | 평가 스크립트 수동 실행 | — |
| 적재 배치 | 변경 이력 기반 자동 동기화 | 수동 스크립트 1회 실행 | — |
| 화면 | Vue SPA, 인증, 피드백, 이력 | **Vue 3 + Vite 단일 페이지** (개발은 Vite 프록시, 데모는 FastAPI가 서빙) | 012 |

**stdio 운영 규칙:** MCP 세션은 FastAPI `lifespan`에서 앱 시작 시 한 번 열고 종료 시 닫습니다. 요청마다 프로세스를 새로 띄우지 않습니다. MCP 서버의 로그는 stderr로만 출력합니다. stdout은 JSON-RPC 메시지 통로이기 때문입니다.

**Redis를 쓰지 않는 이유:** 상용과 MVP 모두 별도 캐시·큐 서버를 두지 않습니다. 검토 작업은 AI 서비스가 직접 실행하며 SSE로 진행 상황을 보내므로 작업 큐가 필요 없고, 외부 API 응답 캐시는 MCP 서버 프로세스 안에서 처리합니다. 인스턴스가 여러 개가 되어 캐시를 공유하거나 외부 API 호출량을 전체적으로 제한해야 할 때 ADR-007에 따라 다시 결정합니다.

**MCP 서버 2개를 MVP에 넣는 이유:** 둘 다 외부 API를 얇게 감싸는 일이라 반나절 안에 끝납니다. 그러면서도 "외부 데이터를 MCP 경계로 분리하고, 검증 단계가 원천을 재조회한다"는 이 설계의 핵심 주장을 실제 코드로 보여줄 수 있습니다.
